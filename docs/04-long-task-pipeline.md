# 长任务流水线

> 这套流程是从「给 1156 篇文章、5364 个句子补中文译文」这件事里长出来的：52 个批次、约 20 轮会话、全程零错位。
>
> 但它不专属于翻译。任何「一个人（或一个模型）要在有限上下文里处理几千条数据」的任务都是同一个形状：给 1156 篇打语法标签、生成 3 万道练习题、补全 7200 个词的例句、预烘焙单词音频、重新做难度分级。
>
> 写下这份文档的目的不是复盘，是**下次直接照着做，不用再踩一遍**。

---

## 0. 一句话

**这类任务的成败不在「生成得快不快」，在「错了能不能被发现」。**

一个 5364 项的数组，只要有 1 项错位，整篇译文就会往后串一位——界面上看着完全正常，只是每句中文都对到了下一句英文上。这种错误不会崩、不会报错、不会被用户第一时间注意，但它让 4 小时的工作全部作废。

所以整条流水线的重心在 **S4 校验闸门**，其余五步都是为它服务的。

---

## 1. 三个天生失效模式

动手之前先认清敌人。这类任务一定同时具备这三条：

| 失效模式 | 具体表现 | 后果 |
|---|---|---|
| **上下文有限** | 5364 句 ≈ 40 万 token，一次装不下 | 必须切批，一批只能装 15–25 篇 |
| **错误静默** | 输出少一项 / 多一项 / 顺序错，格式依然合法 | JSON 解析通过、构建通过、界面正常，错在语义层 |
| **不可回滚** | 20 轮里某一轮把数组搞乱了，你无法指出是哪一轮 | 只能全量重做 |

补充一条：**外部依赖不可靠**。最初用 MyMemory 免费接口，跑到第 31 篇开始全面 429（连发 1040 次全失败）。外部 API 的配额、限流、CORS 都是不可控变量，一旦它写在关键路径上，整个任务就随时会停。

> **结论**：让「生成」这一步可以被随意替换（换模型、换人、换 API），把可靠性全部压在**校验**上。这也是后来改成「我自己翻」能无缝切换的原因——只换 S3，S4 一行没动。

## 2. 骨架：六步 + 一道闸门

```
S1 切分          按「最小单元」把总量切成 N 批
S2 导出          batch.json（只含输入，不含任何已经做过的东西）
S3 生成          batch-NNN.json（单批、单一职责、格式固定）
S4 校验  ←—— 命门。结构 + 数量 + 完整性，任一不符直接拒收
S5 合入          幂等写入，可重放，保留每批原始文件
S6 回归          build + 全量测试，每轮必跑
```

### S1 切分：按「最小单元」，不按字数

批的大小要按**校验单元**来定，不是按字符数。

翻译的校验单元是「句子」，所以一批 18–25 篇（约 100–130 句）是舒适上限。lv2 时 25 篇能一次过；到 lv7（C1 长句、修辞装置密集）就必须降到 18 篇，否则注意力会滑——**长句里丢掉原文的停顿位置，是最难自查的错**。

### S2 导出：批次文件只装输入

`scripts/next-batch.mjs`：

```bash
node scripts/next-batch.mjs --n 18 --level 7
# → data/tr-inbox/batch.json：[{ id, s(标题), lv, x: ["句1", "句2", ...] }]
```

关键点：**导出时就用与运行时完全相同的切句函数**去切句子。如果导出用一套规则、渲染用另一套，那么「句数一致」这个校验就失去意义了——它校验的是导出端自己。

### S3 生成：单批单一职责，格式死板

产物固定为 `{ id: [译文1, 译文2, ...] }`，不加任何注释、不嵌套、不合并文件。批次文件编号 `batch-001 … batch-052` 全部留在 `data/tr-inbox/`，任何一句都能回溯到它的来源批次。

这样做的代价是文件多；收益是**任何一轮出问题，都能定位到具体哪一批、重跑那一批**。

### S4 校验：硬闸门（核心）

`scripts/import-tr.mjs` 只做三件事，但只要有任何一条不过就整批拒收：

```js
1. 结构：是不是 { id: string[] }
2. 数量：译文数组长度 === 该文章的实际句数   ← 命门
3. 覆盖：ids 是否都存在于 articles.json（防止 id 拼错导致静默丢稿）
```

**为什么第 2 条是命门**：它把「大部分正确」变成了「要么全对、要么拒收」。没有它，少一项的批次会被安静地合入，然后整篇错位。这道闸门在早期**拒收了 8 次**，每一次都是我自己切错句——如果没有它，这 8 篇会带着错位进入最终数据，而界面看起来完全正常。

### S5 合入：幂等 + 可重放

`import-tr.mjs` 不删除、不清空，只按 id 覆盖。同一批次文件重复执行结果一致。这样「修一版 → 重新合并」是安全动作，不需要先想清楚怎么撤销。

### S6 回归：每轮必跑

```bash
npm run build        # 必须过（类型 + 打包）
npm run test         # e2e 47→49 项全过
```

数据变了必须重跑测试。这不是形式：`tr.json` 的读取路径、`articles.json` 的 id 对齐、`names.json` 的加载都在这条链上，任何一处错了构建也能通过，只有断言能抓到。

## 3. 三个实战坑（附根因与修法）

### 3.1 句数校验是命门——但它的前提是「切句规则只有一份」

**现象**：早期 8 个批次被拒，全是同一个原因。

```text
原文：  "Not at all," answered Lord Henry, "not at all, my dear Basil."
```

切句器的规则是「`.!?` + 可选引号 + 空白」才算句界，所以这在它眼里是**一句**。而我按视觉上的引号把它切成 3 段，数组就多了 2 项。

**根因**：人眼对着引号断句，机器对着标点断句。两者永远不一致，只能**以机器为准**。

**修法**：不修切句器（它没错），修我的判断——所有对话中「逗号 + 引号」的地方绝不切。

**通用化**：任何「以 A 的切分结果去校验 B 的产出」的流程，都必须保证 A 是**唯一权威**。如果导出端和渲染端各有一份实现，两份迟早会漂移。

**写这份文档时，我发现这条原则自己没做到。**

当时的实际情况是：`src/lib/sentences.ts` 里一份、`scripts/next-batch.mjs` 里一份、`scripts/import-tr.mjs` 里一份，共三份。而且**已经漂移了**——3.2 那次给 `ABBR` 加 `i` 只改了运行时那一份，两个脚本还是老版本，仍在按「`MRS.` 独立成句」切。

后果是隐性的：那 3 篇已修好的文章，如果以后再走一次「导出 → 翻译 → 合入」，导出端会重新切出那个幻影句，校验端也按老规则认账，于是**已经对齐的数据被重新写歪**。两边都「自洽」，却和渲染端不一致。

所以做了一次重构，把切句抽成唯一实现 `src/lib/split.js`（纯 ESM，浏览器和 Node 都能直接 import）：

```
src/lib/split.js          ← 唯一实现（ABBR_RE + splitSentences）
src/lib/sentences.ts      ← export { splitSentences }  再包一层类型
scripts/next-batch.mjs    ← import from '../src/lib/split.js'
scripts/import-tr.mjs     ← import from '../src/lib/split.js'
scripts/verify-tr.mjs     ← import from '../src/lib/split.js'
```

`realign-tr.mjs` 是唯一的例外，它**故意**保留旧正则（`ABBR_OLD`）——它的职责就是重放历史、找出差异，用新规则就失去意义了。这类「迁移工具」允许持有历史版本，但必须在文件里写明原因。

> **教训**：原则写在文档里不等于代码里成立。落文档时必须回头 grep 一遍，确认「只有一份」是真的只有一份。

### 3.2 切句器 × 全大写缩写：修一个 bug 会动到已完成的 1156 篇

**现象**：《绿山墙的安妮》开头被切成两项——`MRS.` 和 `Rachel Lynde lived just where…`。因为切句器的缩写保护表写成了区分大小写的 `\b(Mrs)\.`，而旧书排版常把称谓排成全大写 `MRS.`。

**修法**：`ABBR` 正则加 `i` 标志。

**副作用**：加 `i` 之后 3 篇文章的句数各少 1。**句数一变，已经存好的译文数组就整体错位一格**——注意，这不是报错，是静默的。

**这是整件事里最危险的一刻**：一个看起来只是「让切句更准」的改动，会让 5364 句译文全部对错位。

**修法 2（迁移脚本）**：`scripts/realign-tr.mjs` 重放**旧切法**，找出「新旧切法差异的那一处」，把两段译文合并回一段。

碎片有两种形态，必须都覆盖——只写第一种会漏：

| 形态 | 例子 | 合并后 |
|---|---|---|
| 整句就是一个缩写 | `MRS.` + `Rachel Lynde lived…` | 雷切尔·林德太太就住在… |
| 句尾停在缩写 | `MY DEAR MR.` + `SHERLOCK HOLMES,–You…` | 亲爱的夏洛克·福尔摩斯先生：——您这一手… |

**通用化**：**任何改变切分规则的改动，都是一次数据迁移**，不是一次代码修改。必须准备迁移脚本 + 全量校验，不能「改完跑一下看起来没事就提交」。

迁移后立刻做全量对齐校验（1156 篇逐篇比对句数），确认 5364 句无一处错位。

### 3.3 专名统计：冠词是「这不是专名」的强信号

**目标**：`Matthew` 被当成生词列在提示条里，注的是「马太, 马太福音」。要一份专名表，让句子解析跳过人名地名。

**第一版（错的）**：统计「首字母大写 + 不在句首 + 出现 ≥3 次 且小写形式少」。

**结果**：把寓言里的 **Fox / Lion / Ape / Peacock / Bramble / Monkey / Hare** 全收进了专名表。

而这恰恰是 Aesop 里最该注释的词。`the Fox` 看起来像专名（它确实是角色名），但它是普通名词，学习者正需要「狐狸」这个提示。

**第二版（对的）**：加一条排除——**前一个词是冠词/限定词时不计入**。

```js
const DETERMINER = /^(the|a|an|this|that|these|those|his|her|their|my|your|our|any|some|another|every|each|no|one|two|three)$/i;
if (!atStart && !DETERMINER.test(prev)) midCaps.set(surface, ...);
```

误收从 8 个降到 2 个（`Crab`/`Hare`/`Woodman` 这类仍是角色名，可接受）。最终表 **192 项、1.7 KB**。

**通用化**：做统计型启发式规则时，**先找反例，再写规则**。找反例最快的办法是拿领域里最典型的一批样本去撞规则——寓言动物就是这个领域的反例集合。规则写完之后，也要固化一个「疑似误收清单」的探针。

### 3.4 长度对得上，内容可能是空的

把切句统一之后，顺手写了个常驻的全量校验 `scripts/verify-tr.mjs`（`npm run verify`）。第一次跑就报了 6 篇、共 **8 处空句**：

```
○ sherlock-0008 第 1 句为空     "Quite so!"
○ alice-0004   第 1 句为空     "Alas!"
○ alice-0025   第 4 句为空     "No, no!"
○ anne-0030    第 9/10/11 句为空
```

两类根因：

1. **早期 MyMemory 管线里有一句 `if (s.length < 12) out.push('')`**——太短的句子不值得翻译，于是写了空串。而 `import-tr.mjs` 的闸门只检查「数组长度 === 句数」，空串照样过。**长度校验挡不住内容缺失**，这是闸门本身的盲区。
2. `anne-0030` 尾部三句是配额耗尽那批留下的半成品。

顺带还发现一句明显的机翻硬错：

```
原句：I do wish she'd lived long enough for me to remember calling her mother.
误译：我真希望她活得足够长，让我记得打电话给她的母亲。      ← calling = 打电话
正译：我真希望她能活得久一些，让我还记得叫她一声妈妈。
```

**修法**：断言从「数量对」升级为「数量对 **且** 每格非空」，空句单独计数并列出位置。8 处补齐后重跑，全绿。

补丁本身也走了同一条通道（`data/tr-inbox/fix-001.json` → `import-tr.mjs`）——**修数据也要过闸门，不允许手改 `tr.json`**，否则下次没人知道这处改动是怎么来的。

## 4. 把骨架迁移到别的长任务

骨架不变，变的只有三格：**最小单元 / 硬闸门 / 静默错误长什么样**。

| 任务 | 最小单元 | 硬闸门（S4） | 静默错误形态 |
|---|---|---|---|
| **句子译文** | 句子 | 译文数组长度 === 切句结果长度 | 整篇错位一格 |
| **语法标签**（给每句标主谓/从句/时态） | 句子 | 标签数 === 句数 **且** 标签值 ∈ 枚举白名单 | 标签合法但标给了下一句 |
| **练习题生成**（每篇 3 道） | 文章 | 篇数 === 请求篇数 **且** 每题 answer 必须能在原文中检索到 | 题目自洽但答案不在原文里，玩家永远答不对 |
| **释义补全**（7200 词） | 词 | 词条数 === 7200 **且** 主键去重后无缺失 | 释义张冠李戴（`slight` 给了「轻蔑」，应为「轻微的」） |
| **单词音频烘焙** | 词 | 文件数 === 词数 **且** 每个文件时长 > 100ms | 空音频 / 静音文件，播了没声 |
| **难度重分级** | 文章 | 每档篇数守恒（总数不变） | 某档变空，玩家解锁后无内容 |

写这张表的方法：**先问「这一项错了，界面会表现出什么？」** 如果答案是「看不出来」，就必须造一个能看出来的闸门。

几个具体的闸门写法建议：

- **语法标签**：不要只校验数量，校验**值域**。模型很爱发明 `past-perfect-continuous-passive` 这种不存在的标签，JSON 合法、数量对得上，但渲染时静默丢标签。
- **练习题**：答案必须回原文检索（`tx.includes(answer)` 或词形归一后检索）。这一条能挡掉绝大多数幻觉题。
- **音频**：校验时长 + 首尾静音占比，而不是文件存在。

## 5. 四条纪律

1. **每轮的产物都要落盘，且带编号。** 不合并成大文件、不覆盖上一批。合并是 S4 之后的事。
2. **任何「让结果更准」的规则改动，先假设它会破坏已有数据。** 改切句 → 准备迁移；改词性判断 → 重算全量并抽查；改专名表 → 跑反例探针。
3. **闸门只做拒收，不做修补。** 校验函数里出现「这里少一项那就补个空字符串」这种逻辑，等于把静默错误制度化。
4. **每轮结束跑一次全量回归。** `npm run verify`（译文对齐）+ `npm run build` + `npm run test`。数据链路上任何一环断了，构建都不会报错，只有这三条能抓到。
5. **修数据也要走通道。** 不允许手工编辑 `public/data/tr.json`。补丁写成 `data/tr-inbox/fix-NNN.json`，同样过 `import-tr.mjs` 的闸门——这样每一处改动都有来源、有校验、可回溯。

## 6. 实测数据

| 指标 | 数值 |
|---|---|
| 总量 | 1156 篇 / 5364 句 |
| 批次 | 52 个（`data/tr-inbox/batch-001…052.json`） |
| 会话轮次 | 约 20 轮 |
| 单轮吞吐 | 45 篇 → 83 篇（随规则内化而提升） |
| 闸门拒收 | 早期 8 次（全是切句分歧），后期归零 |
| 全量校验发现的空句 | 8 处（长度校验的盲区，见 3.4） |
| 切句实现份数 | 3 份（已漂移）→ 1 份（`src/lib/split.js`） |
| 数据体积 | `tr.json` 0.55 MB，`dist` 合计 4.1 MB |
| 外部 API 尝试 | MyMemory 跑到第 31 篇后 429，连发 1040 次全失败 → 弃用 |

**一个反直觉的观察**：吞吐提升不是因为翻得快，是因为**返工归零**。前两轮每轮有 3–4 篇被拒、要重新拆批重写；规则内化之后，最后 10 轮没有一次返工。所以「先把校验规则想清楚」比「加快速率」有效得多。

## 7. 已知缺陷 / 下一步

1. **没有 schema 版本号。** `tr.json` 只有 `{v:1, map}`，如果以后译文结构要带「译注」字段，无法区分新旧。应在文件头加 `schema`，读取端做兼容。
2. ~~**合入不是事务。**~~ **已修（2026-11-01）。** 原实现是「逐篇校验、逐篇写入、不合格的跳过」，于是 `garden-0000` 少一句被拒时，同批的 `dorian-0001` 照样被写进去了。我在验证这个行为时，用它把 `dorian-0001` 的真实译文覆盖成了测试串——正是这类事故的样子：**没有报错，只有数据悄悄变了**。

   现在改成两个阶段：

   | 阶段 | 动作 |
   |---|---|
   | 一 | 全量校验（存在性 / 句数 / 非空），有任一问题 → 打印清单、`exit 1`、**一个字节都不写** |
   | 二 | 全部通过后一次性落盘，写 `.tmp` 再 `rename` |

   顺带删掉了 `x => (typeof x === 'string' ? x : '')` 这种「类型不对就给个空串」的兜底——它把静默错误制度化了：空串能过长度校验，等于给闸门开了个洞。
3. **闸门只保证「结构对」，不保证「译得好」。** `verify-tr.mjs` 全绿时，`anne-0030` 里那句把 `calling her mother` 译成「打电话给她的母亲」依然存在——数量对、非空、句子也通顺，只是意思错了。低成本方案：每批随机抽 2 句，与原文对照打出「可读 / 别扭 / 错」三级，连续两批出「错」就停下来重看规则。
4. **专名表句首无解。** 现规则要求「非句首」，所以句首的人名仍会被列出（`Matthew` 已解决，因为它在语料里也出现在句中；但只出现在句首的名字抓不到）。彻底解法是引入外部人名词典。
5. **没有断点续跑的状态文件。** 目前靠「已译集合」反推下一批，逻辑正确但不可观测——加一个 `data/tr-inbox/state.json` 记录「已处理批次 / 当前偏移」，比现算更抗意外中断。
